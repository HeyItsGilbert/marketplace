# Tracker field inventory: GitHub issues vs. local-markdown files

Research note for [issue #54](https://github.com/HeyItsGilbert/marketplace/issues/54), a child of the
`wayfinder-view` map ([#52](https://github.com/HeyItsGilbert/marketplace/issues/52)). No existing
convention covers this kind of cross-adapter research note, so it lives directly under `docs/agents/`
alongside the other agent-facing reference docs. Every claim below is grounded in an actual command run
against this repo or a line in the two source docs — nothing here is guessed.

Sources consulted:

- **GitHub**: `gh issue view <n> --json <bad-field>` (dumps the full allowed-field list as a side effect of
  an error), `gh issue list --json <bad-field>` (same list), live output from issues **52–57** (the
  wayfinder map and its five children) plus a handful of older closed issues (**10–26**), `gh label list`,
  and `gh api repos/HeyItsGilbert/marketplace/issues/<n>` (REST, for the fields the GraphQL-backed `--json`
  flag doesn't surface).
- **Local-markdown**: `/home/gilbert/.agents/skills/setup-matt-pocock-skills/issue-tracker-local.md` (the
  `.scratch/<effort>/` conventions) and `/home/gilbert/.agents/skills/setup-matt-pocock-skills/triage-labels.md`
  (the triage-role → label mapping). This repo's own wayfinder effort uses the GitHub adapter (its
  `docs/agents/issue-tracker.md` is a byte-identical copy of the GitHub doc, and there is no `.scratch/`
  directory in this repo), so the local-markdown shape below is taken from the doc, not from a live example.

## Side-by-side field inventory

| Field | GitHub source | Local-markdown source | Present in both? |
| --- | --- | --- | --- |
| Title | `title` field. `gh issue view 52 --json title` → `"Wayfinder view: render a wayfinder map as a navigable star system"`. | Implicit: the `<slug>` in the filename `issues/NN-<slug>.md`, plus whatever heading the ticket author writes in the body (`issue-tracker-local.md` L26: "with the question in the body"). No dedicated title field/line. | Yes, but GitHub has a structured field and local-markdown only has a filename slug + freeform body heading. |
| Body / question | `body` field. `gh issue view 54 --json body` returns the full markdown body. | The ticket body itself — `issue-tracker-local.md` L26: "Child ticket: `.scratch/<effort>/issues/NN-<slug>.md` … with the question in the body." | Yes. |
| Type | No dedicated field. Convention-only: a `wayfinder:<type>` label. Confirmed live — issue #54 carries `wayfinder:research` (`gh issue view 54 --json labels`), #53/#55/#57 carry `wayfinder:grilling`, #56 carries `wayfinder:prototype`, #52 carries `wayfinder:map`. `docs/agents/issue-tracker.md` L41 documents the `research`/`prototype`/`grilling`/`task` vocabulary. | Dedicated `Type:` line near the top of the issue file — `issue-tracker-local.md` L26: "A `Type:` line records the ticket type (`research`/`prototype`/`grilling`/`task`)." | Yes — same four-value vocabulary, but GitHub encodes it as a label (an indirect, queryable-but-not-native-typed signal) while local-markdown has a first-class line. |
| Status / state | Native `state` (`OPEN`/`CLOSED`) + `stateReason` field. `gh issue view 54 --json state,stateReason` → `"state":"OPEN","stateReason":""`. Plus an *implicit* "claimed" signal via `assignees` (empty = unclaimed). | Dedicated `Status:` line, two explicit values — `issue-tracker-local.md` L26/29: "a `Status:` line records `claimed`/`resolved`" and "**Claim:** set `Status: claimed` and save before any work." | Yes, but the vocabularies don't line up 1:1: GitHub's native `state` is open/closed and "claimed" is inferred from `assignees`, while local-markdown folds claimed/resolved into one `Status:` line and has no separate "closed" concept beyond `resolved`. |
| Assignee / claim | Native `assignees` array. `gh issue edit 54 --add-assignee @me` then `gh issue view 54 --json assignees` → `[{"login":"HeyItsGilbert", …}]`. `docs/agents/issue-tracker.md` L44: "**Claim:** `gh issue edit <n> --add-assignee @me`." | No dedicated assignee field — claiming *is* the `Status: claimed` transition (`issue-tracker-local.md` L29). There's no record of *who* claimed it, only *that* it's claimed. | Partially — both have a claim concept, but only GitHub records an identity; local-markdown just flips a status word. |
| Labels | Native `labels` array (name/color/description/id). `gh label list` in this repo shows the labels actually in use: GitHub defaults (`bug`, `documentation`, `duplicate`, `enhancement`, `good first issue`, `help wanted`, `invalid`, `question`, `wontfix`), the five `wayfinder:*` type labels (`map`/`research`/`grilling`/`prototype`/`task`), and `ready-for-agent`. Cross-checking `gh issue list --state all --json labels` across all 18 issues in the repo confirms only `wayfinder:*` and `ready-for-agent` are actually applied — no `bug`/`enhancement`/etc. have been used yet. | No equivalent construct. The closest analogue is the `Type:` line (one of four fixed values, not an open label set). | No — GitHub-only. Local-markdown has nothing resembling an arbitrary tag/label set. |
| Priority / size | **Not in use.** `gh label list` has no `priority:*`, `size:*`, `P0`/`P1`, or T-shirt-size labels defined in this repo, and none of the 18 sampled issues (open or closed) carry anything resembling one. GitHub issues *can* carry a size/priority label by convention, but this repo doesn't. | No field at all — `issue-tracker-local.md` has no priority or size line in its documented shape. | No — absent on both sides in practice, though GitHub's label mechanism *could* carry one if the repo adopted a convention; local-markdown has no slot for it even in principle. |
| Triage role (needs-triage / needs-info / ready-for-agent / ready-for-human / wontfix) | Labels, per `triage-labels.md` (all five roles map 1:1 to identically-named labels). `ready-for-agent` is confirmed live on closed issue #26 (`gh issue view 26 --json labels`). | Not addressed by `issue-tracker-local.md`; `triage-labels.md` documents "the label strings used in this repo's issue tracker" without naming an adapter, but local-markdown's only state-tracking line is `Status:` (`claimed`/`resolved`), which has no slot for a triage role. | Effectively GitHub-only in this repo's current setup — the triage vocabulary assumes a label mechanism that local-markdown doesn't have. |
| Parent / map linkage | Native `parent` field (GitHub sub-issues). `gh issue view 54 --json parent` → `{"number":52, "title":"Wayfinder view: …", "url":"…/issues/52", …}`. Also native `subIssues` / `subIssuesSummary` on the parent side: `gh issue view 52 --json subIssues` lists all five children with number/state/title/url; REST confirms via `sub_issues_summary`: `{"completed":0,"percent_completed":0,"total":5}`. Fallback documented in `docs/agents/issue-tracker.md` L41 for repos without sub-issues enabled: a task list in the map body plus a `Part of #<map>` line at the top of the child body (and #54's actual body does start with `Part of #52`, belt-and-braces with the native link). | No native linkage field. The map/child relationship is purely structural: the map is `.scratch/<effort>/map.md` and children are files under `.scratch/<effort>/issues/` in the same effort directory (`issue-tracker-local.md` L25–26). Membership is "lives in the same directory," not an explicit parent pointer on the child. | Yes as a concept, but the mechanisms differ completely: GitHub has a queryable native field (plus a textual fallback); local-markdown has only directory co-location. |
| Blocking / dependencies | Native `blockedBy` / `blocking` fields (GitHub issue dependencies). `gh issue view 55 --json blockedBy` → one node, issue #54. `gh issue view 54 --json blocking` → one node, issue #55. REST equivalent: `gh api repos/HeyItsGilbert/marketplace/issues/54 --jq .issue_dependencies_summary` → `{"blocked_by":0,"blocking":1,"total_blocked_by":0,"total_blocking":1}` — note this REST summary counts **open** blockers only (the live gate), per `docs/agents/issue-tracker.md` L42. Fallback for repos without the dependencies feature: a `Blocked by: #<n>, #<n>` line at the top of the child body. | Dedicated `Blocked by: NN, NN` line near the top of the issue file — `issue-tracker-local.md` L27: "a `Blocked by: NN, NN` line near the top. A ticket is unblocked when every file it lists is `resolved`." Numbers are bare ticket numbers (`NN`), not file paths or `#`-prefixed. | Yes — same concept both sides, and GitHub's own *fallback* for repos without native dependencies is textually identical in spirit to local-markdown's only mechanism. The difference: GitHub's native form is a structured, queryable graph edge with an open/closed-aware summary count; local-markdown's is a plain-text line the reader must parse and cross-reference against each listed file's `Status:`. |
| URL / canonical address | Native `url` (web) and `id`/`node_id` (GraphQL) — `gh issue view 54 --json url` → `https://github.com/HeyItsGilbert/marketplace/issues/54`. REST also exposes `html_url` (same value) and a numeric database `id` (`gh api repos/.../issues/54 --jq .id` → `5705066734`), which is what the dependencies-POST endpoint requires (`docs/agents/issue-tracker.md` L42) — distinct from both the `#54` issue number and the `node_id`. | No URL at all. The only address is the filesystem path, `.scratch/<effort>/issues/NN-<slug>.md` — not a link, not dereferenceable outside the checkout. | No — GitHub-only. Local-markdown's "address" degrades to a relative file path. |
| Comments / conversation | Native `comments` field (list of `{author, body, createdAt, …}`). `gh issue view 54 --json comments` (0 comments at research time); `gh issue comment <n> --body "…"` appends one. | Append-only `## Comments` heading at the bottom of the ticket file — `issue-tracker-local.md` L11: "Comments and conversation history append to the bottom of the file under a `## Comments` heading." | Yes, but GitHub's is structured (author, timestamp, separate from body) while local-markdown's is unstructured markdown appended under one heading. |
| Resolution / answer | No dedicated "answer" field — the resolution *is* the closing comment (`gh issue comment` + `gh issue close`) plus the map's Decisions-so-far line. | Issue type (GitHub's native "Issue Types" feature) | Native `issueType` field exists in the schema but is unset for every sampled issue: `gh issue view 52 --json issueType` → `null`. | Milestone / project board | Native `milestone` and `projectItems`/`projectCards` fields exist in the schema but are empty/null for every sampled issue (`gh issue view 52 --json milestone,projectItems` → `null`, `[]`). Not in use in this repo. | No equivalent. | No — unused GitHub-only fields. |

## Net takeaways

- **GitHub has, and local-markdown lacks:** an open label set (arbitrary tags beyond the four-value type),
  a real dereferenceable URL/database id, structured per-comment authorship and timestamps, native
  parent/sub-issue and blocked-by/blocking graph edges with a live open-only dependency count, and several
  unused-but-present schema fields (`issueType`, `milestone`, `projectItems`) that could carry
  priority/size/triage data if this repo ever adopted them — it currently doesn't.
- **Local-markdown has, and GitHub lacks (or only approximates via convention):** a first-class `Type:`
  line (vs. GitHub's label-as-type convention), a first-class `Status: claimed/resolved` line (vs. GitHub's
  split between native `state` and inferred-from-`assignees` claim status), and a first-class `## Answer`
  section on the child ticket itself (GitHub's answer lives only in the comment thread).
- **Priority/size:** absent on both sides in this repo today. GitHub's label mechanism and unused
  `issueType`/`milestone` fields *could* carry one if adopted; local-markdown's documented shape has no
  slot for it at all.
- **Confirmed-working native features in this repo** (not just documented — exercised live during this
  research): sub-issue parent linkage (#54's `parent` → #52) and issue dependencies (#54 `blocking` → #55,
  #55 `blockedBy` → #54), both via `gh issue view --json` and cross-checked against the REST
  `issue_dependencies_summary`/`sub_issues_summary` endpoints.
